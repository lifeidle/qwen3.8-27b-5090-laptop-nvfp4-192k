## 1. 项目概述

**背景**：Qwen3.8-27B 是 27.8B 稠密多模态模型（Gated DeltaNet + Gated Attention 混合架构，262,144 原生上下文，内嵌 MTP 投机解码头，Apache-2.0）。它的 BF16 权重约 55.6 GB，远超消费级单卡容量——在 24GB 笔记本上部署必须依赖社区量化。

**问题**：社区生态在发售后数周内涌现了 **50+ 个量化变体**（多个家族 × 多个精度档位），质量与性能差异众说纷纭，缺乏统一平台上的横向实测。

**本项目做了什么**：
- 系统性盘点全部主流量化家族（53 个变体）
- 用统一方法学实测入围选手（速度 / 容量 / 质量三维度）
- 对胜出者进行逐层调优（KV 量化、MTP 参数、上下文极限、引擎版本、散热）
- 给出可复现的最终配置与工具脚本

**最终成果**：找到了这台机器上"质量无损前提下"的速度与容量双最优解，并验证其在长时间满载下的稳定性。

## 4. 测试方法

全部测试基于 **llama.cpp 的 `/completion` 与 `/v1/chat/completions` 端点 + 服务端 timing 日志**，方法学要点：

| # | 测试项 | 方法 |
|---|---|---|
| 1 | **KV 显存校准** | 双点差值法：同一模型跑 ctx=8192 与 ctx=32768 两个实例，读 `nvidia-smi` 显存占用差值 → 得出每 token KV 开销（排除权重与固定开销） |
| 2 | **上下文容量扫描** | 逐档试启动（F16 / q8_0 / q4_0 / 混合 KV），成功点与失败点的 `cudaMalloc` 错误量确定精确临界 |
| 3 | **生成速度** | 固定 256-token prompt（temperature 0.7），多轮采样取均值，记录 `predicted_per_second` 与 MTP 草稿接受率 |
| 4 | **长 prompt 处理** | 15,614-token 中文长文档（大海捞针构造），记录端到端耗时与 `prompt eval` 吞吐 |
| 5 | **MTP 参数扫描** | n-max ∈ {2,3,4,5} × p-min ∈ {无, 0.75} 全组合启动测试 |
| 6 | **代码质量** | 同题对决：单文件贪吃蛇游戏（5 项明确需求），检查完整性、功能覆盖、隐藏 bug |
| 7 | **长文召回** | 大海捞针：12K token 文档（暗号埋 70% 深度）+ 150K token 文档（埋 80% 深度） |
| 8 | **引擎版本对比** | 同一模型同一参数跑 b10840 与 b10889，对比生成与 prefill |
| 9 | **散热压力** | 12 分钟连续 512-token 生成负载，每轮记录 tok/s + 温度 + 功耗 + SM 时钟 |
| 10 | **质量基线** | `reasoning_effort` 档位对照（xhigh 默认 vs medium） |

**测试纪律**：所有对比均在"同模型/同上下文/同 KV 类型/同 MTP 参数/同引擎"条件下进行；速度测试均多轮采样；每次服务切换后确认显存干净（<700 MiB 基线）。

## 5. 测试结果

### 5.1 上下文容量：KV 量化是关键

**物理上限的实测**（以 IQ3_S 为例，双点法测得每 token KV 开销 ≈ 65 KiB @ F16）：

| KV 类型 | IQ3_S 最大上下文 | q8_0 相对 F16 容量提升 |
|---|---|---|
| F16（默认） | 136K | — |
| **q8_0（K/V）** | **212K** | **+56%** |
| K q8_0 + V q4_0 | 262K（满血） | +93% |
| q4_0（K/V） | 262K（满血） | +93% |

**⚠️ 重大发现：q4_0 系 KV 存在"慢路径"**——它能开满 262K，但长 prompt 处理速度断崖式劣化：

| 配置 | 15.6K prompt 耗时 | 判定 |
|---|---|---|
| 32K + F16 | 13.6 s | ✅ 基准 |
| 136K + F16 | 15.2 s | ✅ 无惩罚 |
| **200K + q8_0** | **15.1 s** | ✅ **无惩罚** |
| 262K + q4_0 系 | **~420 s（未跑完）** | ❌ **慢 28 倍**（attention kernel 回退，速度从 286 tok/s 超线性衰减到 29 tok/s） |

**结论**：**q8_0 是 KV 量化的最优解**（零速度惩罚 + 质量近无损 + 容量 +56%）；q4_0 系虽然容量更大，但长 prompt 场景完全不可用。

### 5.2 三方速度对决（同条件：各自最大上下文 + q8_0 KV + MTP n-max 3）

**引擎 b10840（旧）下的对决**：

| 模型 | 配置 | 生成均值 | 15.6K prefill | 接受率 |
|---|---|---|---|---|
| **NVFP4-LOW** | 152K | **74.7 tok/s** | **10.1 s** | 63% |
| IQ3_S | 212K | 61.9 tok/s | 15.5 s | 65% |
| UD-Q4_K_S | 152K | 58.3 tok/s | 15.2 s | 73%（最高）|

**引擎 b10889（新）下的重测**：

| 模型 | 配置 | 生成均值 | 15.6K prefill | 最大上下文 |
|---|---|---|---|---|
| **NVFP4-LOW** | **192K（推荐）/ 200K（极限）** | **79.6 tok/s** | **9.7 s** | 200K |
| IQ3_S | 212K（可到 240K） | 64.4 tok/s | 14.9 s | 240K |
| UD-Q4_K_S | 200K | 51.7 tok/s | 19.9 s | 200K |

**速度差异的机制解释**：
- **NVFP4-LOW 为什么最快**？它的头部设计（Q5_0 输出层 + IQ4_XS MTP 头）让每次 MTP 验证 pass 与草稿 pass 的读取成本最低——社区在 RTX 5090 上发现同样规律（LOW 是该家族吞吐冠军）。
- **UD 为什么接受率最高（73%）却最慢**？K-quant 的每轮验证成本最贵（dequant 开销），且无 FP4 硬件加速：净效果垫底。
- **NVFP4 的 FP4 张量核优势只体现在 prefill**：两个 NVFP4 模型的 prefill 都是 10 秒级，K-quant 则是 15–20 秒级。

### 5.3 质量验证：三方打平

**代码质量**（贪吃蛇同题）：

| 维度 | IQ3_S | NVFP4-MID-HIGH | UD-Q4_K_S |
|---|---|---|---|
| 完整可运行 | ✅ | ✅ | ✅ |
| 5 项需求覆盖 | ✅ | ✅ | ✅ |
| 防反向自杀缓冲 | ✅ | ✅ | ✅ |
| 食物避开蛇身 | ✅ | ✅ | ✅ |
| **尾节排除**（高级细节） | ✗ | ✗ | **✅（唯一）** |
| 输出长度 | 3,985 字符 | 5,624 字符 | 4,164 字符 |

**长文召回**：三方全部通过（12K/70% 与 150K/80% 深度的暗号全部准确召回）。

**结论：三个量化在质量上打平**。UD-Q4_K_S 在经典细节上最严谨（小幅体现其 4.4bpw 的纸面精度优势），但不足以构成代差。

### 5.4 MTP 参数扫描：当前参数已是最优

| 配置 | LOW 生成均值 | IQ3_S | UD | 判定 |
|---|---|---|---|---|
| **n-max 3** | **74.4** | **63.2** | **59.3** | 🏆 三方共同最优 |
| n-max 2 | 66.7 | 61.0 | 54.7 | 慢 7–10% |
| n-max 4 | 启动崩（差 594 MiB） | 63.5（@200K，无收益） | 未测 | 不可用 / 无收益 |
| n-max 3 + p-min 0.75 | 64.6（接受率虚高至 85%） | — | — | 吞吐 -13% |

**关键洞察**：**n-max 4 的验证批次需要约 594 MiB 额外显存**——在 24GB 卡的贴边配置下不可用；且即便可用也无收益。**接受率高 ≠ 速度快**（p-min 0.75 把接受率从 63% 抬到 85%，速度反降 13%）。

### 5.5 引擎版本对比（b10840 → b10889）

| 模型 | 旧引擎 | 新引擎 | 差异 |
|---|---|---|---|
| **NVFP4-LOW** | 74.7 / 152K / 10.1s | **79.6 / 200K / 9.7s** | **+6.6% 速度，+48K 容量** |
| IQ3_S | 61.9 / 212K / 15.5s | 64.4 / 212K / 14.9s | +4% |
| UD-Q4_K_S | 58.3 / 152K / 15.2s | 51.7 / 200K / 19.9s | **-11%（无益）** |

**结论**：新版引擎的优化**主要惠及 NVFP4 模型**（FP4 路径 + 显存管理改进，后者让 LOW 的可用上下文直接 +48K）；K-quant 未见受益。

**⚠️ 迁移注意**：新版移除了 `--no-mmap`，替代参数为 **`--load-mode none`**。

### 5.6 散热压力测试（12 分钟 / 100 轮连续满载）

| 指标 | 首轮 | 末轮 | 判定 |
|---|---|---|---|
| 生成速度 | 78.7 tok/s | 83.7 tok/s | **零衰减** |
| GPU 温度 | 55 °C | 77 °C（稳定平台） | 安全区间 |
| 功耗 | 132 W | 145 W | 稳定 |
| SM 时钟 | 1830 MHz | 1740 MHz | -5%（轻微） |

**结论：笔记本散热完全扛得住长时间 agent 负载**——速度无系统性衰减，无需担心热降频。

## 6. 关键发现（八条可复用经验）

1. **`reasoning_effort` 是必设项**：Qwen3.8-27B 默认推理强度（xhigh）会产生极长思考——实测 **8000 token 全部烧在思考里、正文零输出**。必须显式传 `{"chat_template_kwargs":{"reasoning_effort":"medium"}}`（medium 档 11 秒收敛出完整代码）。社区 4800 任务受控测试亦证实：xhigh 比 low 多烧 7–11 倍 token，只换 0–4.7 分。**永远不要关闭 reasoning**（NVFP4 关闭时 HumanEval+ 从 90 跌到 13/30）。

2. **q4_0 系 KV 有隐藏的性能悬崖**：容量看似最优（262K），但 attention kernel 回退导致长 prompt 处理慢 28 倍。**q8_0 KV 才是甜点**（零惩罚 + 近无损 + 容量 +56%）。

3. **MTP 在 dense 模型上是纯收益**：n-max 3 实测提速 +79%（IQ3_S）/ +73%（NVFP4），接受率 60–80%。与 MoE 模型上"MTP 反而减速"的经验相反（MoE 的专家读取惩罚在 dense 上不存在）。但 n-max 4+ 需要额外 ~594 MiB 显存，小显存卡不适用。

4. **MTP 接受率高 ≠ 速度快**：速度取决于"每 pass 成本 × 每 pass 收益"。小头部设计（LOW 的 Q5_0 lm_head + IQ4_XS MTP head）让每 pass 更便宜，即使接受率不是最高也能最快。p-min 过滤会抬高接受率但降低吞吐。

5. **NVFP4 的 FP4 加速只在 prefill 兑现**：decode（逐 token 生成）是带宽受限——NVFP4 模型文件更大（14.5 GiB vs IQ3_S 的 11.3 GiB），理论上 decode 应更慢；但小头部设计的 NVFP4-LOW 实测反而最快。**prefill 上 NVFP4 全面领先（10s vs 15s 级）**。

6. **新引擎的收益与量化类型强相关**：b10840→b10889 给 NVFP4 带来 +6.6% 速度 + 48K 容量（显存管理改进），给 K-quant 带来 -11%。**升级引擎后必须重测容量**（可用上下文可能显著变化）。

7. **大上下文对 K-quant 不友好**：NVFP4-LOW 在 200K 上下文的 prefill 仍是 9.7s（与 152K 时持平），而 UD-Q4_K_S 在 200K 时 prefill 从 15.2s 掉到 19.9s。KV 量化 + 大分配对 K-quant 的 dequant 路径影响更大。

8. **prompt cache 是最大的免费加速**：同一段 15.6K 输入，首次处理 15 秒，缓存命中后仅 **2.3 秒（6.5×）**。agent 长会话中保持对话前缀稳定（勿频繁改动系统提示词）即可持续享受。

## 7. 最终推荐配置

### 🏆 主力配置（日常代码 Agent）

```
模型：Qwen3.8-27B-NVFP4-MTP-LOW.gguf（14.47 GiB）
引擎：llama.cpp b10889（或更新的官方构建）
参数：-ngl 99 -fa on -fit off -c 192000 --cache-type-k q8_0 --cache-type-v q8_0
      --load-mode none --jinja --spec-type draft-mtp --spec-draft-n-max 3
性能：生成 79.6 tok/s · 15.6K 输入 9.7 秒 · 最大上下文 200K（推荐 192K）
质量：与 BF16 的差距在社区受控测试中不可测（4bit 全族与 FP8 统计打平）
```

### 备胎配置（超长材料专用）

```
模型：DASLab GSQ-RCO IQ3_S-MTP（11.29 GiB）
参数：同上，-c 212000（极限可到 240K）
性能：生成 64.4 tok/s · 15.6K 输入 14.9 秒
理由：任务无损学术背书；NVMe 占用最小
```

### 通用 API 调用要求（三者共通）

```json
{
  "messages": [...],
  "chat_template_kwargs": { "reasoning_effort": "medium" }
}
```
思考模式采样：`temp 1.0 / top_p 0.95 / top_k 20`；非思考模式：`temp 0.7 / top_p 0.80 / top_k 20`。
